Краткое описание предметной области

Программа моделирует модуль учета личных финансов для банковского приложения «ТигрБанк», позволяя пользователям управлять счетами, 
категориями доходов/расходов и операциями, а также анализировать финансовые потоки для планирования бюджета и достижения финансовых целей.

Используйте единый code style:
// PascalCase или Upper camelCase для классов
JsonExporter, CreditAccount, MainMenuScreen

// camelCase для методов и переменных
getAvailableCredit(), openDebitAccount(), accountService

Добавьте модульное теcтировани

Модульное тестирование в проекте построено на базе одного эталонного теста MenuTest, 
который демонстрирует ключевой подход к проверке взаимодействия между классами с использованием Mockito: 
создается заглушка (mock) зависимого компонента, выполняется тестируемый метод, после чего с помощью verify проверяется факт вызова нужного метода у заглушки.
Этот тест служит фундаментом для дальнейшего масштабирования тестового покрытия на все слои приложения — модель, сервисы и команды.
Проведена интеграция JaCoCo для автоматического измерения процента покрытия кода с генерацией детализированных отчетов, а также в перспективе планируетсяподключение Allure 
для визуализации результатов тестирования, формирования понятных дашбордов и встраивания этих отчетов в CI/CD пайплайн, что обеспечит прозрачный контроль качества на всех этапах разработки.

Структура теста (AAA Pattern)
Общая концепция
Тестирование может быть построено по принципу пирамиды тестирования, обеспечивающей оптимальный баланс между скоростью выполнения, 
надежностью и стоимостью поддержки. Основной фокус — на модульных тестах как фундаменте качества, с постепенным надстраиванием интеграционных и E2E-тестов.

Соблюдайте принципы SOLID

Программа в целом соблюдает основные принципы SOLID. Принцип единственной ответственности реализован через четкое разделение на слои (модель, сервисы, UI, экспорт), 
где каждый класс отвечает за свою узкую область. Принцип открытости/закрытости обеспечивается абстрактным классом и интерфейсами, что позволяет расширять функциональность новыми типами счетов, 
команд или экспортеров без изменения существующего кода. Принцип подстановки Лисков соблюдается в иерархии наследования — наследники Account корректно замещают родительский класс. 
Принцип разделения интерфейса реализован через специализированные интерфейсы с минимальным набором методов. Принцип инверсии зависимостей частично реализован через внедрение зависимостей 
в конструкторы классов, хотя некоторые компоненты по-прежнему сами создают свои зависимости, что требует доработки для полного соответствия принципу.

Реализуйте взаимодействие модулей через DI-контейнер

В текущей реализации программы используется ручное внедрение зависимостей через конструкторы, что является основой для работы с DI-контейнером, 
однако полноценный контейнер пока не задействован — многие классы по-прежнему сами создают свои зависимости с помощью оператора new. 
При рефакторинге эта проблема может быть устранена путем вынесения конфигурации зависимостей в отдельный слой и использования DI-контейнера, например Spring Boot,
что позволит автоматически управлять жизненным циклом объектов, внедрять зависимости через конструкторы и сделать систему более гибкой, тестируемой и полностью соответствующей принципу инверсии зависимостей.

Укажите ситуации, при которых появятся проблемы добавления нового функционала или расширении бизнес-логики

1. Жесткая связанность с выводом в консоль

Проблема: Логика предметной области (Account, CreditAccount) напрямую вызывает System.out.println().
При расширении: При попытке добавить графический интерфейс или веб-интерфейс придется менять код модели, нарушая SRP.

2. Отсутствие DI-контейнера в некоторых участках кода

Проблема: MainMenuScreen сам создает все сервисы через new.
При расширении: Добавление нового сервиса потребует изменения конструктора MainMenuScreen и всех мест, где он используется.

3. Ручной поиск зависимостей

Проблема: AccountService.findByNumber() сам перебирает всех клиентов.
При расширении: При добавлении нового способа хранения (БД, кэш) придется переписывать логику поиска во всех сервисах.

4. Нарушение инкапсуляции в сервисах

Проблема: Сервисы принимают другие сервисы как параметры (например, AccountService.findByNumber(..., CustomerService)).
При расширении: Цепочки зависимостей растут, код становится хрупким и трудно поддерживаемым.

5. Отсутствие интерфейсов для сервисов

Проблема: Сервисы работают напрямую с конкретными классами, а не с интерфейсами.
При расширении: Невозможно подменить реализацию (например, для тестов или новой БД) без изменения кода.

6. Логика в модели, которая должна быть в сервисах

Проблема: Транзакции и валидация размазаны по классам модели.
При расширении: При добавлении новых правил (комиссии, лимиты, валютный контроль) придется менять множество классов.


Аргументы, почему введенные абстракции улучшили качество дизайна

1. Абстрактный класс Account

Проблема без абстракции: Логика всех типов счетов была бы в одном классе с множеством условных операторов.
Улучшение: Вынесение общего поведения в базовый класс и реализация специфики в наследниках позволило избавиться от ветвлений, 
сделать код понятнее и подготовить систему к появлению новых типов счетов без изменения существующего кода.

2. Интерфейс MenuCommand

Проблема без абстракции: Логика всех пунктов меню была бы в одном огромном классе с гигантским switch.
Улучшение: Каждая команда стала отдельным классом с единой точкой входа execute().
Это позволило изолировать изменения, легко добавлять новые пункты меню и тестировать каждую команду независимо.

3. Интерфейс ReportExporter

Проблема без абстракции: При добавлении нового формата отчета пришлось бы менять код генерации отчетов.
Улучшение: Теперь можно регистрировать новые экспортеры динамически, не трогая существующий код. 
Система стала расширяемой и соответствует принципу открытости/закрытости.

4. Фабрика TransactionFactory

Проблема без абстракции: Создание транзакций было размазано по всему коду с дублированием логики.
Улучшение: Централизация создания объектов транзакций устранила дублирование, гарантировала единообразие и упростила изменение формата транзакций.

5. Выделение сервисного слоя (Bank, AccountService и др.)

Проблема без абстракции: Бизнес-логика была смешана с моделью и UI.
Улучшение: Сервисный слой стал мостом между моделью и представлением, что позволило переиспользовать бизнес-логику, тестировать ее изолированно и подменять реализации при необходимости.
