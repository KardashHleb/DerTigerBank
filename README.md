Ключевые архитектурные изменения

В ходе рефакторинга были последовательно применены следующие паттерны и принципы:

1. Инверсия управления (IoC) и Внедрение зависимостей (DI)
Классы создавали необходимые им зависимости через new, что приводило к жесткой связности и усложняло тестирование.
Во все классы команд (CreateAccountMenuCommand, AnalyticsCommand, BankReportCommand и др.) зависимости теперь передаются через конструктор.
Пример (CreateAccountMenuCommand):
Было: new OpenDebitAccountCommand(bank, io) внутри метода.
Стало: Конструктор получает готовые OpenDebitAccountCommand и OpenCreditAccountCommand.
Результат: Соблюден Dependency Inversion Principle (DIP). Классы высокого уровня больше не зависят от конкретных реализаций низкого уровня. Система готова к использованию DI-контейнера.

3. Применение паттерна Фасад (Facade)
Проблема: Сложная логика работы с банковскими счетами, категориями и операциями была разбросана по всей программе, что нарушало принцип High Cohesion.
Решение:
Bank теперь выступает в роли Фасада для бизнес-логики. Он скрывает за собой взаимодействие с репозиториями, фабриками и сервисами, предоставляя простой интерфейс для команд UI.
MainMenuScreen стал Фасадом для пользовательского интерфейса, координируя отображение меню и вызов соответствующих команд.
Возможные улучшения в дальнейшем: создание дополнительных фасадов (например, CategoryFacade, OperationFacade) для дальнейшего улучшения структуры.
Результат рефакторинга: Упрощен интерфейс взаимодействия, повышена связность внутри модулей и снижена связность между ними (Low Coupling).

4. Применение паттерна Команда (Command)
Проблема: Каждый пользовательский сценарий был просто функцией или процедурой, что затрудняло управление транзакциями, очередями и историей операций.
Решение: Каждый сценарий (создание счета, вывод отчета, аналитика) инкапсулирован в отдельный класс-команду.
Все команды имеют интерфейс.
Пример: CreateAccountMenuCommand, AnalyticsCommand, BankReportCommand.
Результат: Сценарии стали взаимозаменяемыми, их легко параметризировать, логировать и ставить в очередь.

5. Применение паттерна Шаблонный метод (Template Method)
Проблема: Код для импорта данных из CSV, JSON и YAML содержал много дублирования (чтение файла, валидация, сохранение) — нарушение DRY (Don't Repeat Yourself).
Решение:
Создан абстрактный класс BaseReportImporter, содержащий шаблонный метод importReport().
Этот метод определяет общий алгоритм импорта, делегируя специфичную для формата часть (парсинг) абстрактному методу parseFile().
Конкретные реализации: CsvReportImporter, JsonReportImporter, YamlReportImporter переопределяют только метод парсинга.
Для создания нужного импортера используется ImporterFactory.
Результат: Устранено дублирование кода, упрощено добавление новых форматов файлов, соблюден принцип Open/Closed (OCP).

6. Устранение жестких зависимостей через интерфейсы
Проблема: Прямое использование конкретных классов (например, Bank, ConsoleIO) не позволяло легко подменять их реализации для тестов или расширения.
Решение: Введение интерфейсов для ключевых компонентов:
AccountProvider (для предоставления данных о счетах)
BankService (для выполнения банковских операций)
InputOutput (абстракция для ввода-вывода вместо ConsoleIO) и других интерфейсов в папке - интерфейсы
Результат: Код теперь зависит от абстракций, а не деталей. Это позволяет, например, легко создать MockInputOutput для юнит-тестов или заменить консольный ввод на GUI.

7. Рефакторинг доменных моделей и сервисов
НЕКОТОРЫЕ ПРИМЕРЫ:
TransactionType: Введен enum для типов транзакций (доход/расход), что повышает типобезопасность и читаемость кода по сравнению с использованием строк или чисел.
TransactionFactory: Инкапсулирует сложную логику создания объектов Transaction, гарантируя их целостность (например, автоматическая установка даты).
AnalyticsService: Выделен в отдельный сервис, взяв на себя ответственность за аналитические расчеты (разница доходов/расходов, группировка по категориям). Это разгрузило Bank (Facade) и повысило High Cohesion.
StorageService: Упрощен за счет делегирования ответственности за создание и импорт объектов другим классам (TransactionFactory, ImporterFactory).

Связь с требованиями задачи
SOLID:
SRP: Каждый класс имеет одну причину для изменения.
OCP: Система открыта для расширения (новые форматы импорта через ImporterFactory, новые команды и др.).
LSP: Реализации импортеров и команд могут быть взаимозаменяемы.
ISP: Интерфейсы (InputOutput, AccountProvider) узкоспециализированы.
DIP: Модули верхнего уровня не зависят от модулей нижнего уровня, все зависят от абстракций (благодаря DI).
GRASP:
High Cohesion: Достигнута благодаря выделению AnalyticsService, TransactionFactory и фасадов.
Low Coupling: Достигнута благодаря DI и интерфейсам.
Паттерны GoF: Применены Фабричный метод, Фасад, Команда, Шаблонный метод.
Функциональность: Вся требуемая функциональность (аналитика, импорт/экспорт, управление данными) сохранена и улучшена.

Продолжено развитие тестового покрытия, тесты направлены на тестирование основной функциональности. Шаблон для написания тестов ААА.

Ситуации, приводящие к проблемам без рефакторинга
До рефакторинга добавление нового функционала требовало изменений в существующем коде: поддержка нового формата импорта (XML) заставила бы копировать логику импортеров 
и добавлять новые switch-case во все места выбора формата. 
Смена консольного ввода на GUI потребовала бы переписывания всех классов, напрямую использующих ConsoleIO, а добавление новой аналитики — модификации монолитного класса Bank, нарушая принцип открытости/закрытости (OCP).

Почему абстракции улучшили дизайн
Введенные абстракции (интерфейсы) обеспечили Low Coupling и High Cohesion.
Теперь классы зависят от абстракций, а не деталей реализации: AnalyticsCommand получает готовый AnalyticsService через конструктор (DIP),
а новый формат импорта добавляется созданием подкласса без изменения существующего кода (OCP), что делает систему гибкой и легко расширяемой.
